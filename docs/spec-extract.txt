PRECISION FARMINGMVP — IMPLEMENTATION SPECIFICATIONWeb React + TypeScript • iOS Swift • Android Kotlin • Backend KotlinSingle Backend • Demo Data • Google Maps Satellite • Production-shaped Architecture
Versão: 1.0 — Documento destinado a uma IA de codificação/autonomous coding agent. O objetivo é transformar esta especificação em um protótipo MVP funcional, executável localmente, com dados demo realistas e paridade funcional entre Web, iOS e Android.
IMPORTANTE: o MVP deve ser realmente executável. Não criar telas estáticas ou mocks desconectados. Todas as telas devem consumir o mesmo backend e persistir dados no banco. Integrações externas que exigem credenciais devem possuir adapters reais + modo demo determinístico.
1. Objetivo do documento
Este documento é o contrato de implementação do MVP do Precision Farming. Uma IA de codificação deve conseguir gerar o repositório, executar os serviços, popular o banco com dados demo, iniciar Web/iOS/Android e demonstrar os fluxos principais sem depender de integrações proprietárias.
• Web: React.js + TypeScript.
• iOS: Swift + SwiftUI, aplicativo nativo separado.
• Android: Kotlin + Jetpack Compose, aplicativo nativo separado.
• Backend: Kotlin + Spring Boot.
• Banco: PostgreSQL + PostGIS.
• Mapas e imagens de satélite: Google Maps Platform.
• Todos os clientes consomem o mesmo backend.
• Dados demo devem ser persistidos e editáveis.
• Arquitetura preparada para integrações futuras, mas MVP deve funcionar sem elas.
• UI deve ser clean, fluida, responsiva, acessível e orientada a tarefas.
2. Regras não negociáveis para a IA de codificação
1. Não gerar apenas wireframes; implementar comportamento real.
2. Não criar APIs fake dentro do frontend; usar HTTP contra o backend.
3. Não duplicar regra de negócio em Web/iOS/Android.
4. Não armazenar estado de negócio crítico apenas localmente.
5. Não usar dados aleatórios em runtime; usar seed determinístico.
6. Não colocar API keys do Google em código-fonte versionado.
7. Não expor credenciais server-side no frontend.
8. Não criar microserviços desnecessários para o MVP; começar com modular monolith bem delimitado.
9. Não usar dados de satélite falsos quando o mapa Google estiver disponível.
10. Não substituir a imagem real do Google Maps por uma imagem estática.
11. Não esconder erros de integração: mostrar status, retry e modo demo.
12. Todo endpoint deve possuir teste.
13. Todo fluxo crítico deve ter teste end-to-end.
14. Manter Web/iOS/Android com a mesma matriz funcional.
15. Documentar decisões que divergem desta especificação.

5. Arquitetura do MVP
O backend deve ser um modular monolith, não um conjunto inicial de microserviços. Os módulos devem ter fronteiras claras para permitir extração futura.
• auth — identidade, usuários, roles.
• farm — farms, units, fields, crops.
• asset — machines, implements, sensors.
• telemetry — observations, positions, metrics.
• weather — providers, forecasts, observations.
• operation — plans, work orders, executions.
• inventory — items, batches, movements, applications.
• alert — rules, alerts, acknowledgements.
• ai — features, predictions, recommendations.
• geo — geometry validation and map metadata.
• integration — connector registry and adapters.
• reporting — exports and aggregations.
• notification — in-app notifications.

O backend é a fonte de verdade dos dados de negócio. O Google Maps é uma camada de visualização/geospatial experience; não usar o backend como proxy de tiles do Google.
7. Google Maps Platform — requisito obrigatório
O mapa deve usar dados reais do Google Maps Platform. No Web, usar Maps JavaScript API; ela suporta mapas interativos, marcadores, dados customizados e tipos de mapa como SATELLITE e HYBRID. Para o MVP, o mapa deve iniciar em SATELLITE quando o usuário estiver no módulo de talhões. citeturn0search5turn0search9
No Android, usar Maps SDK for Android nativo, com MAP_TYPE_SATELLITE ou MAP_TYPE_HYBRID e overlays de polígonos/markers. O SDK suporta markers, polygons, polylines e interação com mapa. citeturn0search0turn0search3
No iOS, usar Maps SDK for iOS nativo e mapType .satellite ou .hybrid. O SDK expõe GMSMapView e permite markers, polylines e polygons. citeturn1search0turn1search16turn1search17
Google exige billing ativo e chave válida para o uso dos SDKs/serviços. As chaves devem ser restritas por aplicação/API; não colocar uma chave unrestricted no repositório. A recomendação é uma chave Web restrita por HTTP referrer, uma chave Android por package/SHA-1 e uma chave iOS por bundle identifier, conforme as capacidades/restrições suportadas. citeturn0search2turn0search4turn1search1

19. IA & Insights — MVP
O MVP deve ter modelos determinísticos/estatísticos com interface preparada para ML real. Não apresentar um algoritmo fictício como modelo treinado.
• Yield forecast: baseline calculado sobre dados demo.
• Machine failure risk: score baseado em horas, falhas e telemetria demo.
• Operational delay risk: score baseado em backlog + weather.
• Input deviation: comparação planejado × realizado.
• Weather window score.
• AI recommendation card com confidence, rationale e timestamp.
Toda previsão deve indicar: 'Demo model' no ambiente demo, modelo/version, data/hora e confiança. O sistema deve possuir endpoint para substituir o modelo por um serviço Python posteriormente.

22. API conventions
• Prefix /api/v1.
• UUIDs para entidades.
• ISO-8601 UTC para timestamps.
• Pagination cursor-based quando necessário.
• Consistent error envelope.
• Correlation ID em cada request.
• Idempotency-Key para comandos.
• ETag/If-Match para updates sensíveis quando apropriado.
• Validation com Bean Validation.
• OpenAPI gerado.
• HTTP status semânticos.
• Não retornar entidades JPA diretamente.

38. Google Maps e camadas agrícolas
A base Google deve permanecer como mapa real. As camadas agrícolas são do Precision Farming: polygons de talhões, markers, trajectories e overlays próprios. Não misturar a propriedade intelectual de mapas Google com imagens agrícolas demo sem identificar a origem.
• Base: Google Satellite.
• Overlay 1: Field boundaries.
• Overlay 2: Machine locations.
• Overlay 3: Machine track.
• Overlay 4: Operations.
• Overlay 5: Weather station.
• Overlay 6: Demo NDVI layer.

39. NDVI demo
Como o Google Maps fornece a base de satélite, mas não deve ser tratado como uma API de NDVI agrícola, o MVP pode apresentar um raster/overlay NDVI próprio e claramente identificado como 'Demo NDVI'. A arquitetura deve permitir substituir posteriormente por imagens e produtos reais de satélite.
Cada raster deve possuir source, acquisitionAt, processingVersion, resolution e quality.

57. Limitações e decisões explícitas
• Google Satellite não substitui um pipeline agronômico de NDVI.
• Dados demo de telemetria não representam telemetria real de um fabricante.
• Conectores reais dependem de APIs, contratos, permissões e disponibilidade do fornecedor.
• Modelos de IA demo não devem ser apresentados como modelos agronômicos validados.
• Forecast demo não deve ser tratado como previsão meteorológica real.
• O MVP é tecnicamente preparado para integrações reais, mas não deve fingir que elas estão conectadas.
• Imagens Google devem ser usadas conforme os termos/licenciamento aplicáveis.
58. Resultado esperado
Ao final do MVP, Precision Farming deve parecer e funcionar como um produto real, não como uma coleção de telas. O usuário deverá conseguir observar a fazenda em um mapa real, entender o estado dos talhões e máquinas, planejar e executar operações, acompanhar clima e alertas, consultar insights preditivos e trabalhar pelo mobile mesmo com conectividade intermitente.
A arquitetura deve permitir que o MVP seja posteriormente expandido para conectores reais de fabricantes, drones, sensores, satélites, mercado agrícola e modelos de machine learning sem reescrever os clientes ou o domínio central.
